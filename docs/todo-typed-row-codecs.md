# TODO: Schema-Backed Row Helpers

This document records the work needed to remove handwritten per-family
`rows.rs` byte packing. Materialized rows still exist, and projectors still
decide when to emit them. The change is that row shape becomes protocol-owned
schema metadata interpreted or generated by core tooling, rather than hidden in
manual offsets inside each fact family.

This TODO is about rows only. Fact `encode.rs` / `decode.rs` migration stays in
the fact pipeline reorg; the staged read/write pipeline remains:

```text
READ:   fact bytes -> decode -> authenticate -> adapt -> project -> effects
WRITE:  command -> author -> encode -> authenticate(self-check) -> admit -> READ
```

## Boundary

Core may learn row fields from schema declarations. The rule is not that core
must be blind to protocol structure; the rule is that core must not contain
hand-written protocol-specific branches.

- Protocol owns row declarations: table name, key fields, value fields, field
  types, stable order, intro/version metadata when needed, and semantic helper
  names.
- Core owns generic row machinery: table registration, encode/decode,
  encoded-length checks, key-prefix construction, delete selector construction,
  allowlist enforcement, and debug/introspection.
- Projectors own materialization policy: semantic fact plus context becomes
  generated row insert/delete helper calls.
- Queries own read semantics: they call generated decoders and key-prefix
  helpers instead of hand-decoding opaque bytes.

## Why The Current Code Exists

Core row mutations currently store protocol-owned rows as opaque `(table, key,
value)` bytes. That keeps commits idempotent and keeps core from directly
importing auth, connection, content, or sync row types.

The current `rows.rs` files therefore build `TableRow` values directly:

```rust
let mut value = vec![0; ROW_VALUE_BYTES];
value[0..32].copy_from_slice(&fact.from_endpoint);
value[32..64].copy_from_slice(&fact.to_endpoint);
```

This is correct but too low-level. The layout is fixed-width and deterministic,
but the offsets are invisible policy. Every added field requires synchronized
manual edits to length constants, encode offsets, decode offsets, and tests.

## Problems To Fix

- Offset arithmetic hides field names and makes reviews harder.
- Encode and decode can drift when fields are inserted or reordered.
- Length constants duplicate what the field list already implies.
- Row layouts look different from fact layouts even when they need the same
  fixed-width discipline.
- Simple row modules become noisy, which obscures the projector policy that
  decides when rows are written.
- `rows.rs` looks like a permanent fact-family role file even though row shape is
  schema, not projection logic.

## Target Shape

Replace handwritten `rows.rs` modules with schema-backed generated helpers.

Each row declaration should provide enough information to generate or interpret:

- table metadata and allowlist entry
- key field schema and value field schema
- `encoded_len` for key and value
- `encode_key`, `encode_value`, `decode_key`, `decode_value`
- row constructor helpers that still return `TableRow` / `TableDelete`
- key-prefix helpers for common query patterns
- delete selector helpers for keyed deletes and retention/projector cleanup
- golden round-trip tests for key and value bytes

Generated helpers may live under a generated module or be re-exported with the
old helper names during migration. The desired end state is no handwritten
per-family byte packing file named `rows.rs`.

## Candidate Designs

### Declarative Row Schema

Add protocol-owned row declarations, likely near the existing schema source:

```rust
row_table! {
    table bootstrap_request_rows {
        key {
            request_id: Bytes32,
        }
        value {
            from_endpoint: Bytes32,
            to_endpoint: Bytes32,
            invite_fact_id: Bytes32,
            invite_secret_fact_id: Bytes32,
            initiator_ephemeral_secret_fact_id: Bytes32,
        }
    }
}
```

The generated type owns encode/decode, byte length, key-prefix helpers, delete
selectors, and row-value round trips. `project.rs` and `queries.rs` call
generated helpers.

### Transitional Row Cursor

A `RowWriter` / `RowReader` helper can be used only as a migration bridge:

```rust
let mut row = RowWriter::<BOOTSTRAP_REQUEST_VALUE_BYTES>::new();
row.bytes32("from_endpoint", fact.from_endpoint);
row.bytes32("to_endpoint", fact.to_endpoint);
row.bytes32("invite_fact_id", fact.invite_fact_id);
```

This removes offset arithmetic but still leaves handwritten row modules. Use it
only when a full schema declaration is too large for the current step.

### Reuse Existing Fact Codecs Where Exact

Some rows intentionally store the same bytes as a fact payload. In those cases,
prefer reusing the fact codec or a shared generated layout type instead of
defining a second row codec. Only do this when row semantics exactly match fact
semantics; projection rows often omit authority fields or add query-specific
fields.

## Migration Plan

1. Inventory every `rows.rs` file and classify manual offset packing, key-prefix
   helpers, delete helpers, query-only helpers, and semantic helper names.
2. Add schema-backed row declarations and generic core row machinery.
3. Land the model conversions:
   `auth/workspace` uses `SchemaSource.row_schemas` for an opaque key/value row,
   and `content/message` removes `rows.rs` by using registry typed-table schemas
   directly from `project.rs` and `queries.rs`.
4. Convert the next representative fixed-width opaque row family:
   `connection/request`.
5. Generate equivalent constructors, decoders, key-prefix helpers, delete
   selectors, table metadata, and allowlist metadata.
6. Update `project.rs` and `queries.rs` to call generated helpers.
7. Add golden tests that prove the new helpers emit the same bytes as the old
   implementation.
8. Remove the representative handwritten `rows.rs`.
9. Add a guardrail test that flags new per-family `rows.rs` files and direct
   `value[N..M].copy_from_slice(...)` row packing outside an explicit temporary
   allowlist.
10. Convert the rest of the connection rows, then auth/content/sync rows.
11. Remove each allowlist entry as its row family moves to schema-backed helpers.
12. Commit the completed work on that same worktree branch before handoff or
    review.

## Tests

Each conversion should include realistic tests:

- Existing row bytes remain stable for golden fixtures.
- Decode rejects wrong-length row keys and values.
- Encode/decode round trips preserve every named field.
- Row-key and key-prefix helpers are unchanged.
- Delete selector helpers target the same keys/ranges as before.
- Projector tests still observe the same materialized rows.
- Query tests still decode and sort rows the same way.
- Guardrails prevent new handwritten row packing and shrink the temporary
  `rows.rs` allowlist over time.
